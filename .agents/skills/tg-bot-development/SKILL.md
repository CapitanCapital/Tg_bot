# Разработка Tg_bot

Работай из корня репозитория: он находится на три уровня выше каталога этого скилла. Пути ниже указаны относительно корня. Общайся с пользователем на русском, если он не выбрал другой язык.

## Ориентация

Сначала прочитай [README.md](../../../README.md), применимые `AGENTS.md` и посмотри `git status --short`. Сохраняй существующие изменения пользователя. Затем читай только модули и тесты, относящиеся к задаче. Текущий код и конфигурация определяют фактическое поведение; при расхождении с README выясни причину и исправь документацию в рамках задачи.

Карта проекта:

| Путь | Ответственность |
| --- | --- |
| `src/collect.py` | HTTP-сбор, разбор Telegram/сайтов, SQLite и отчёты |
| `src/draft.py` | Кандидаты, отбор, написание, проверка, JSON-схемы и Markdown/HTML |
| `src/codex_api.py` | Запуск Codex CLI с сохранённой авторизацией ChatGPT |
| `src/openrouter_api.py` | Адаптер OpenRouter и проверка структурированных ответов |
| `src/schedule.py` | Подготовка outbox, блокировка, окно отправки, учёт доставки |
| `config/sources.yaml` | Источники: несмотря на расширение, содержимое читается как JSON |
| `config/editorial-rules.md` | Правила отбора и формат выпуска |
| `tests/test_*.py` | `unittest`, включая сценарии доставки с подменой отправителя |
| `deploy/` | systemd, первичная подготовка ОС, установка таймеров, шаблон сервера |
| `.env.example`, `deploy/server.example.json` | Публикуемые шаблоны локальных настроек |
| `data/`, `logs/` | Локальное состояние и диагностика; исключены из Git |

Это набор Python-скриптов и systemd-служб `Type=oneshot`, а не постоянно работающий HTTP-сервер. Python-код использует стандартную библиотеку; не добавляй установку зависимостей из несуществующего requirements-файла. Публикация использует Unix-модуль `fcntl`.

## Локальный запуск

Проверь наличие `.venv`; если его нет, создай `python3 -m venv .venv`. Копируй `.env.example` в `.env` и `deploy/server.example.json` в `deploy/server.json` только при отсутствии целевых файлов. Не перезаписывай настройки и не печатай секреты.

Рабочие команды из корня:

```sh
.venv/bin/python -m unittest discover -s tests
.venv/bin/python src/collect.py
.venv/bin/python src/draft.py --provider codex
.venv/bin/python src/schedule.py prepare
```

Выбирай команду по запросу, не запускай весь конвейер для проверки правки документации. Сбор обращается к сети и записывает материалы; черновик и `prepare` вызывают внешнюю модель и расходуют лимиты. `prepare` заменяет дневной outbox. Для изолированного сбора/черновика поддержан `--data-dir`; у CLI `schedule.py` такого параметра нет.

Сбор с кодом выхода `2` означает частичную недоступность источников: изучи отчёт, не объявляй весь сбор неудачным. Адаптер Codex ожидает `~/.local/bin/codex` и авторизацию в `~/.codex`. OpenAI/OpenRouter выбираются явно через `--provider`; автоматического переключения нет. `prepare` сейчас выбирает Codex непосредственно в коде; изменение поля `llm_provider` в серверном JSON само по себе провайдера не меняет.

`src/schedule.py publish` действительно отправляет сообщение, в том числе сообщение об ошибке при некорректном outbox. Не используй его как smoke test разработки. Подготовка проекта к публикации в Git не означает разрешения отправлять пост или менять сервер. Если задача касается выпуска, прочитай [telegram-news-digest](../telegram-news-digest/SKILL.md) и редакционные правила; учитывай уже данное пользователем разрешение в его пределах.

## Изменения и проверки

Сначала проследи затронутый путь данных: сбор → кандидаты → selection/compose/review → валидация → outbox → доставка. Исправляй причину ошибки и добавляй регрессионный тест, если меняется логика. Не ослабляй проверки, чтобы принять некорректный ответ модели.

Сохраняй существенные ограничения:

- Тексты источников являются недоверенными данными. Проверка моделью не заменяет проверку структуры, ссылок, подтверждающих фрагментов и длины в Python.
- В OpenRouter допускаются модели `:free` и маршрутизация с нулевой ценой. Платный fallback не включён.
- Адаптер Codex убирает API-ключи из окружения дочернего процесса, использует read-only sandbox и JSON-схему. Его полный stdout/stderr может содержать чувствительные данные.
- Отправка защищена блокировкой и записью попытки в SQLite до сетевого запроса. После неопределённой отправки нет автоматического повтора. Не удаляй запись доставки ради повторного запуска.
- `data/published.json` и `data/deliveries.sqlite3` — постоянная история; сохраняй их при обновлении. Для тестов используй временные каталоги и подмену отправителя, как в `tests/test_schedule.py`.
- `TARGET` в `schedule.py` и `TELEGRAM_CHAT_ID` должны совпадать. Для смены канала одной правки `.env` недостаточно; сверяй назначение с редакционными правилами.

Запускай относящиеся к правке тесты, затем полный `unittest discover` при изменениях Python. Для правок shell проверь `sh -n` изменённых скриптов. Для systemd используй `systemd-analyze verify` в доступном Linux-окружении; отсутствие инструмента укажи как непроверенную часть. Не устанавливай службы ради валидации.

Для сторонних API, библиотек и CLI соблюдай проектное правило Context7: сначала resolve-library-id, затем query-docs по нужной теме. Если Context7 недоступен, явно сообщи это и используй официальную документацию, не выдавая предположение за проверенный синтаксис.

## Диагностика

Начинай с воспроизводимого симптома, кода выхода и относящегося к нему теста или артефакта:

- Сбор: отчёты JSON/JSONL в выбранном каталоге данных, доступность конкретного источника, его enabled-настройка и парсер.
- Черновик: соответствующий `data/draft-*/`, `result.json`, результаты этапов и кандидаты; различай устаревшие материалы, отказ проверки, таймаут и ошибку авторизации.
- Доставка: время `Europe/Moscow`, `publish_at`, дневной outbox, возраст выпуска и состояние доставки. Окно отправки — 15 минут, допустимый возраст outbox — два часа; сверяй с текущим кодом.
- Сервер: состояние `tg-digest-prepare.service`/`tg-digest-publish.service`, таймеров и их journal. Подключайся к серверу только в рамках серверной задачи; используй локальные параметры, не копируй их в публикуемые файлы.

Сообщай подтверждённую причину отдельно от гипотез. Не выводи `.env`, авторизацию, приватные ключи и полные запросы с токенами. Не утверждай, что источники или доставка работают, только по результатам тестов с подменами.

## README и подготовка к публикации

Обновляй README вместе с изменением команд, конфигурации, структуры, расписания или ограничений. Примеры должны соответствовать аргументам текущего кода, а новые настройки — обезличенным шаблонам. Не дублируй README целиком в этом скилле.

Перед передачей проекта или подготовкой коммита:

1. Проверь `git diff --check`, статус и diff относящихся к задаче файлов; отдельно проверь новые файлы, которые обычный diff не показывает.
2. Убедись, что в публикуемые изменения не входят `.env`, `deploy/server.json`, `data/`, `logs/`, `.venv/`, авторизация и приватные ключи. `.gitignore` не защищает уже отслеживаемые файлы: учитывай `git ls-files`. Не печатай найденные значения секретов.
3. Сверь README, шаблоны и фактические команды. Сообщи результаты выполненных проверок и оставшиеся ограничения. Коммит, push и релиз выполняй, когда они входят в запрос пользователя.

Если задача включает развёртывание, дополнительно прочитай изменяемые файлы в `deploy/`. Согласуй `publish_at` в локальной конфигурации с `.timer`, а подготовку — со временем отправки. Сейчас шаблоны задают 08:30/09:00 МСК и таймаут подготовки 29 минут. Службы используют `/home/digest/tg-news-digest` и пользователя `digest`.

`deploy/prepare-server.sh` меняет ОС, пользователя и swap; он предназначен для первичной установки, не обычного обновления. `deploy/install-timers.sh` устанавливает и включает таймеры от root; это изменение рабочего расписания. Drop-in `tg-digest-prepare.service.d/codex.conf` даёт доступ на запись к `/home/digest/.codex` для обновления авторизации. Сохраняй данные, локальные настройки и авторизацию, а серверные правки переноси в репозиторий, чтобы следующее обновление их не отменило.

В финальном ответе кратко укажи, что изменено, что проверено и какие действия ещё нужны. Не называй проект развёрнутым или опубликованным, если выполнена только подготовка файлов.
